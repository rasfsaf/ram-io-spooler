# RAM Write-Behind Scribe Engine (ram-io-spooler)

Высокоскоростная подсистема буферизации записи в оперативную память (RAM Write-Behind Engine) для серверов с классическими механическими жесткими дисками (HDD). Спроектирована для компенсации медленного случайного ввода-вывода (Random I/O) на Ubuntu 24.04 LTS (HDD Seagate ST3160815AS 160 ГБ, I/O-планировщик BFQ).

Система принимает любые операции записи (файлы, SQLite базы данных, логи, JSON-состояния, двоичные блобы) за **0.02–0.05 мс** в транзитный RAM-буфер (`tmpfs`), дедуплицирует повторяющиеся операции (Write Coalescing), сортирует очередь по путям (LBA/Path Elevator) и последовательно сбрасывает данные на физический диск с гарантированным `fsync()` и мгновенной очисткой ОЗУ (`Zero-Leak Eviction`).

---

## Архитектура и принципы работы

1. **Транзитный RAM-буфер (`/dev/shm/io-spool`):** Запись попадает в оперативную память на скорости ОЗУ без ожидания позиционирования головок HDD.
2. **Write Coalescing (Дедупликация):** Если один и тот же файл или стейт перезаписывается 50–100 раз за интервал сброса (2–5 сек), на физический диск попадает только одна финальная версия (сокращение IOPS до 98%).
3. **LBA / Path Elevator Sorting:** Перед сбросом очередь упорядочивается по директориям и путям, превращая случайный Random I/O в линейный Sequential Write.
4. **Zero-Leak Memory Eviction:** После сброса блока на HDD и подтверждения через `fsync()` память освобождается на всех уровнях:
   - Удаление временного блоба из `tmpfs`.
   - Очистка структур данных в рантайме.
   - Вызов `posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED)`, выгружающий записанные страницы из Linux Page Cache.

---

## Способы взаимодействия

Спулер поддерживает три интерфейса:
- **Python Client (`spooler.client.SpoolerClient`)** — прямое подключение через Unix domain socket `/run/ram-spooler.sock`.
- **Unix Socket REST API (cURL / IPC)** — для bash-скриптов, системных демонов и бэкапов.
- **TCP HTTP REST API (`http://127.0.0.1:8088`)** — универсальный HTTP-интерфейс для любых сервисов и контейнеров.

## Руководство по интеграции

### Вариант 1: Использование в Python коде (рекомендуемый)

```python
from spooler.client import SpoolerClient

client = SpoolerClient()

# 1. Атомарная перезапись файла / конфига / стейта (ATOMIC_WRITE)
# При частых вызовах на диск попадает только финальное состояние (Write Coalescing).
client.write(
    target_path="/home/server/project/state.json",
    data=b'{"status": "active", "updated_at": 1714000000}',
    op_type="ATOMIC_WRITE"
)

# 2. Быстрая дозапись в лог / историю (APPEND)
# Записи накапливаются в памяти и сбрасываются на HDD единой пачкой.
client.append(
    target_path="/home/server/project/app.log",
    data="[INFO] User action completed\n"
)

# 3. Синхронизация SQLite базы данных (SQLITE_SYNC)
# Сбрасывает дамп SQLite на диск с обязательным fsync.
client.sqlite_sync(
    target_path="/home/server/project/data.db",
    data=db_bytes
)

# 4. Принудительный сброс (гарантированная немедленная запись на диск)
client.flush()
```

---

### Вариант 2: Использование через Unix-сокет (Bash / cURL)

```bash
# Атомарная запись через Unix domain socket:
curl --unix-socket /run/ram-spooler.sock http://localhost/spool \
  -H "Content-Type: application/json" \
  -d '{
    "target_path": "/home/server/test.txt",
    "op_type": "ATOMIC_WRITE",
    "text": "Hello HDD"
  }'

# Дозапись в лог:
curl --unix-socket /run/ram-spooler.sock http://localhost/spool \
  -H "Content-Type: application/json" \
  -d '{
    "target_path": "/home/server/app.log",
    "op_type": "APPEND",
    "text": "[INFO] New event\n"
  }'

# Принудительный сброс очереди на физический диск:
curl --unix-socket /run/ram-spooler.sock -X POST http://localhost/flush

# Статистика очереди и RAM-буфера:
curl --unix-socket /run/ram-spooler.sock http://localhost/stats
```

---

### Вариант 3: Использование через локальный HTTP REST API (порт 8088)

Удобно для микросервисов, языков программирования без прямой поддержки Unix domain sockets или внешних скриптов:

```bash
# Запись текстовых данных
curl -X POST http://127.0.0.1:8088/spool \
  -H "Content-Type: application/json" \
  -d '{
    "target_path": "/home/server/app_state.json",
    "op_type": "ATOMIC_WRITE",
    "text": "{\"user_count\": 42}"
  }'

# Запись бинарных данных (в base64)
curl -X POST http://127.0.0.1:8088/spool \
  -H "Content-Type: application/json" \
  -d '{
    "target_path": "/home/server/snapshot.bin",
    "op_type": "ATOMIC_WRITE",
    "data_b64": "AQIDBAU="
  }'

# Просмотр статистики очереди
curl http://127.0.0.1:8088/stats

# Сброс очереди на диск
curl -X POST http://127.0.0.1:8088/flush
```

## Формат API эндпоинтов

| Метод | Эндпоинт | Назначение | Параметры (JSON) |
| :--- | :--- | :--- | :--- |
| `POST` | `/spool` | Постановка задачи на запись в RAM-очередь | `target_path` (str), `op_type` (`ATOMIC_WRITE` \| `APPEND` \| `SQLITE_SYNC`), `text` (str) или `data_b64` (str) |
| `GET` | `/stats` | Мониторинг очереди, задержек и ОЗУ | Нет |
| `POST` | `/flush` | Принудительная синхронизация всех очередей на HDD | Нет |
| `GET` | `/health` | Проверка жизнеспособности демона | Нет |

## Анализ существующих аналогов на рынке

| Технология | Принцип работы | Сильные стороны | Ограничения для наших задач |
| :--- | :--- | :--- | :--- |
| **Linux Page Cache (Dirty Pages)** | Встроенная подсистема ядра Linux. Буферизует запись в кэш страниц и лениво пишет через `flusher threads` (pdflush). | Встроена в ядро, работает прозрачно для всех процессов. | Не делает дедупликацию логических состояний приложения; оставляет страницы в памяти, забивая ОЗУ; `fsync()` от любого приложения блокирует поток до завершения физического ввода-вывода. |
| **bcache / dm-writeboost / dm-cache** | Блочное кэширование (SSD/NVMe в качестве write-back кэша для медленного HDD). | Работает на уровне секторов блочного устройства с высокой скоростью. | Требует наличия второго быстрого накопителя (SSD/NVMe). При падении по питанию без NVRAM есть риски рассинхронизации. Не работает чисто в ОЗУ. |
| **ZFS ZIL / SLOG (RAM / NVRAM)** | Журнал транзакций файловой системы ZFS в оперативной памяти или на энергонезависимом накопителе. | Гарантия консистентности ФС, объединение транзакций (Transaction Groups, txg). | Требует полного переформатирования дисков в файловую систему ZFS и резервирования значительного объема оперативной памяти под ARC (от 2–4 ГБ). На сервере используется ext4. |
| **Redis / KeyDB (как write-behind буфер)** | Приложение пишет в In-Memory хранилище (Redis), а фоновый скрипт или celery worker лениво выгружает данные в СУБД/диск. | Очень быстрая обработка в RAM, богатые структуры данных. | Требует написания специализированной обвязки/воркеров под каждую структуру; не решает задачу произвольных файлов, конфигов и SQLite баз данных; оверхед на сериализацию и память. |
| **Любительские ramdisk-скрипты (tmpfs + cron rsync)** | Копирование рабочего каталога в tmpfs и периодический rsync на HDD по таймеру. | Простота реализации в виде bash-скриптов. | Высокий риск потери данных всего временного окна; пиковые нагрузки на диск во время запуска rsync; отсутствие очереди, статусов, дедупликации и управления жизненным циклом страниц. |
| **Наш `ram-io-spooler`** | Специализированный транзитный RAM-буфер с дедупликацией на уровне сущностей, LBA-сортировкой и автоматической выгрузкой страниц через `fadvise(DONTNEED)`. | Запись 0.02 мс; 98% экономии ресурса HDD; нулевое удержание памяти в RAM; универсальный API (Python, Unix-сокет, HTTP REST); готовность к работе с файлами, логами и SQLite на обычной файловой системе ext4. | Требует интеграции клиентов через API или клиентскую библиотеку для задач, критичных к задержкам диска. |
